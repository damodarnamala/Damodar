Performance and reliability

Learning outcome: Control retries, costs, tokens, rate limits and failure

1. What is it?

Retries handle transient failures but can amplify costs or duplicate side effects. Use exponential backoff with jitter, hard budgets and idempotency keys.

2. Why does it matter?

Measure cost per successfully completed task rather than only cost per token.

Concrete scenario: Recover from temporary provider errors. The figure below names the actual components and shows how information moves among them.

3. Key concepts and vocabulary

ConceptExplanation
Rate limitmaximum permitted request throughput
Backoffgrowing delay between retries
Circuit breakerprevents repeated failing calls
Fallbackalternate safe behavior

4. Topic-specific architecture and execution flow

Every branch is controlled by application code. A model can recommend an action, but it does not automatically gain permission to perform that action. Record observations and check the terminal condition after every step.

5. Step-by-step algorithm

  1. Model request: Process the model request stage, and pass its defined output to the next node.
  2. Rate limiter: Process the rate limiter stage, and pass its defined output to the next node.
  3. Provider call: Process the provider call stage, and pass its defined output to the next node.
  4. Failure classifier: Process the failure classifier stage, and pass its defined output to the next node.
  5. Backoff / breaker: Process the backoff / breaker stage, and pass its defined output to the next node.
  6. Result or fallback: Emit a result only after verifying the stated conditions.

6. Runnable Python lesson

This module links to 05_retries.py. Some modules reuse an earlier example intentionally: revisit it and identify which concept is newly relevant. The downloadable file is in the examples/ folder.

Run locally: python examples/05_retries.py from the extracted project root. Examples using provider libraries also need the dependencies and credentials explained in Setup.
"""Retry transient errors only; do not retry non-idempotent writes blindly."""
import time

def retry(operation, attempts: int = 3, delay: float = 0.01):
    for index in range(attempts):
        try:
            return operation()
        except ConnectionError:
            if index == attempts - 1:
                raise
            time.sleep(delay * (2 ** index))

if __name__ == "__main__":
    calls = [0]
    def flaky():
        calls[0] += 1
        if calls[0] < 3:
            raise ConnectionError("transient")
        return "success"
    print(retry(flaky))

8. Real-world design exercise

You are building a performance and reliability capability for an enterprise assistant. It must complete a user task while preserving authorization, explicit failure states, and observable results.

Build task: Implement bounded exponential retry. Start with one valid scenario, one invalid input and one failure case. Add an explicit max-step or timeout condition and document whether the workflow has side effects.

9. Common mistakes and troubleshooting

  • Retrying permanent authentication errors. Mitigation: make this condition explicit in a test or a runtime policy.
  • Launching unbounded parallel calls. Mitigation: make this condition explicit in a test or a runtime policy.

10. Practice and knowledge check

In reliability backoff circuit breaker, what happens between “Rate limiter” and “Result or fallback”, and what must be checked?

Follow the labeled arrows in the diagram: Rate limiter hands a defined result through the intermediate stages toward Result or fallback. For this topic, explicitly guard against retrying permanent authentication errors.

How do you stop an agent from looping forever?

Use a maximum step count, time limit, cost budget and explicit terminal condition.

How do you prove that the result is correct?

Use independent deterministic validation, trusted source evidence, tests and human approval as appropriate.
