Planning and dependency graphs

Learning outcome: Represent subtasks as a DAG and run only ready tasks

1. What is it?

A dependency graph makes task order explicit. Nodes represent work; edges represent prerequisites. A topological scheduler only selects ready nodes.

2. Why does it matter?

Cycle detection and failure propagation are essential to prevent stuck jobs.

Concrete scenario: Build and test a change in dependency order. The figure below names the actual components and shows how information moves among them.

4. Topic-specific architecture and execution flow

Every branch is controlled by application code. A model can recommend an action, but it does not automatically gain permission to perform that action. Record observations and check the terminal condition after every step.

5. Step-by-step algorithm

  1. Read requirements: Process the read requirements stage, and pass its defined output to the next node.
  2. Design change: Process the design change stage, and pass its defined output to the next node.
  3. Implement: Process the implement stage, and pass its defined output to the next node.
  4. Unit tests: Process the unit tests stage, and pass its defined output to the next node.
  5. Security review: Process the security review stage, and pass its defined output to the next node.
  6. Pull request: Emit a result only after verifying the stated conditions.

Run locally: python examples/04_planner.py from the extracted project root. Examples using provider libraries also need the dependencies and credentials explained in Setup.
"""Deterministic prerequisite scheduler and cycle detection."""
def schedule(tasks: dict[str, list[str]]) -> list[str]:
    result, completed = [], set()
    unknown = {d for deps in tasks.values() for d in deps} - set(tasks)
    if unknown:
        raise ValueError(f"Unknown dependencies: {unknown}")
    while len(completed) < len(tasks):
        ready = sorted(k for k, deps in tasks.items()
                       if k not in completed and set(deps) <= completed)
        if not ready:
            raise ValueError("Dependency cycle")
        result.extend(ready)
        completed.update(ready)
    return result

if __name__ == "__main__":
    tasks = {"requirements": [], "code": ["requirements"],
             "tests": ["code"], "review": ["tests"]}
    print(schedule(tasks))

8. Real-world design exercise

You are building a planning and dependency graphs capability for an enterprise assistant. It must complete a user task while preserving authorization, explicit failure states, and observable results.

Build task: Implement a dependency scheduler. Start with one valid scenario, one invalid input and one failure case. Add an explicit max-step or timeout condition and document whether the workflow has side effects.

9. Common mistakes and troubleshooting

  • Executing tasks before prerequisites complete. Mitigation: make this condition explicit in a test or a runtime policy.
  • Failing to detect cycles in dependencies. Mitigation: make this condition explicit in a test or a runtime policy.

10. Practice and knowledge check

In task dependency dag, what happens between “Design change” and “Pull request”, and what must be checked?

Follow the labeled arrows in the diagram: Design change hands a defined result through the intermediate stages toward Pull request. For this topic, explicitly guard against executing tasks before prerequisites complete.

How do you stop an agent from looping forever?

Use a maximum step count, time limit, cost budget and explicit terminal condition.

How do you prove that the result is correct?

Use independent deterministic validation, trusted source evidence, tests and human approval as appropriate.
