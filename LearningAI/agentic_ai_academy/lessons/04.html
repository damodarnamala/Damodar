Module 04 / 30

Agent algorithms

Learning outcome: Implement ReAct, plan/execute, reflection and stopping conditions

1. What is it?

ReAct alternates between selecting an action and observing its result. Plan-and-Execute creates a preliminary plan first. Reflection adds an evaluation pass, but a critique is not proof of correctness.

2. Why does it matter?

Always cap iterations and require independent validators for important facts or side effects.

Real-world analogy: Think of a restaurant. A request is an order, the agent controller is the manager, tools are the kitchen stations, state is the order ticket, and verification is the final quality check before serving. The manager must not let a kitchen worker authorize a payment on its own.

4. Mental model: execution flow

USER TASK │ ▼ [VALIDATE INPUT & POLICY] │ ▼ [DECIDE / PLAN NEXT STEP]◄───────────┐ │ │ ▼ │ [EXECUTE APPROVED TOOL] │ │ │ ▼ │ [OBSERVE + UPDATE STATE]───────────────┘ │ when complete ▼ [VERIFY / APPROVAL GATE] │ ▼ [RESULT + AUDIT EVENT]

Every branch is controlled by application code. A model can recommend an action, but it does not automatically gain permission to perform that action. Record observations and check the terminal condition after every step.

5. Step-by-step algorithm

Define success: Specify exactly what successful completion means and what artifacts or output are expected.
Validate context: Check user input, available tools, permissions, schemas and remaining budget.
Select a step: Determine the next step using deterministic rules or an LLM where judgment is useful.
Execute safely: Validate tool arguments and run only permitted operations.
Observe and update: Capture results, errors, state changes, and trace events.
Finish or recover: Verify completion, retry transient errors within bounds, or escalate to human review.

# ReAct style (conceptual; model decides the tool request)
while step < max_steps:
    response = model(messages, tools=approved_tools)
    if response.final:
        return verify(response.final)
    for call in response.tool_calls:
        result = dispatch_validated(call)
        messages.append(tool_result_message(call.id, result))
    step += 1

6. Runnable Python lesson

This module links to 01_agent_loop.py. Some modules reuse an earlier example intentionally: revisit it and identify which concept is newly relevant. The downloadable file is in the examples/ folder.

Run locally: python examples/01_agent_loop.py from the extracted project root. Examples using provider libraries also need the dependencies and credentials explained in Setup.
"""No API key needed. A deterministic agent-like tool loop."""
from dataclasses import dataclass

@dataclass
class Action:
    name: str
    a: float = 0
    b: float = 0

def add(a: float, b: float) -> float:
    return a + b

def run(goal: str, max_steps: int = 3) -> str:
    tools = {"add": add}
    history = []
    for _ in range(max_steps):
        if not history:
            action = Action("add", 12, 30) if goal == "add" else Action("final")
        else:
            return f"Result: {history[-1]}"
        if action.name == "final":
            return "Unsupported request"
        if action.name not in tools:
            raise ValueError("Not allowed")
        history.append(tools[action.name](action.a, action.b))
    raise RuntimeError("Step limit")

if __name__ == "__main__":
    assert run("add") == "Result: 42"
    print(run("add"))

7. Code walkthrough

Read the imports first: standard-library imports need no extra package, while third-party imports require installation. Identify the input contract, the primary function or class, and what each return value means. Notice whether the example is fully deterministic or delegates the next-step decision to a model. Pay particular attention to any allowlist, type validation, exception or approval check.

Trace the program manually: (1) create initial input; (2) inspect arguments and state; (3) run the primary function; (4) record returned value; (5) inspect failure path with an invalid input. For framework examples, the model may choose different valid wording or tool calls, so output text is illustrative rather than guaranteed.

8. Real-world design exercise

You are building a agent algorithms capability for an enterprise assistant. It must complete a user task while preserving authorization, explicit failure states, and observable results.

Build task: Compare two algorithm traces. Start with one valid scenario, one invalid input and one failure case. Add an explicit max-step or timeout condition and document whether the workflow has side effects.

9. Common mistakes and troubleshooting

  • Assuming the model is an authority: keep permissions in trusted application code.
  • Unbounded loops: always cap tool calls, elapsed time and cost.
  • Confusing output with verification: validate schemas, citations, tests or user approvals.
  • Missing state boundaries: define what gets saved and when recovery is safe.
  • Running incompatible imports: install packages in a virtual environment and check official migration notes.

10. Practice and knowledge check

What should happen if the model asks for a prohibited tool?

The trusted runtime rejects it and records an error; the model never gets implicit privileges.

How do you stop an agent from looping forever?

Use a maximum step count, time limit, cost budget and explicit terminal condition.

How do you prove that the result is correct?

Use independent deterministic validation, trusted source evidence, tests and human approval as appropriate.
