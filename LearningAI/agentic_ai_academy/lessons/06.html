Prompts and context engineering

Learning outcome: Assemble trustworthy, budgeted context and instructions

1. What is it?

Context engineering chooses what information enters the model window. Keep trusted instructions separate from retrieved webpages or tool data. Retrieved content is evidence, not authority.

2. Why does it matter?

Use consistent structured sections for goal, rules, context, tools and success criteria.

Concrete scenario: Combine trusted instructions with retrieved, untrusted text. The figure below names the actual components and shows how information moves among them.

4. Topic-specific architecture and execution flow

Every branch is controlled by application code. A model can recommend an action, but it does not automatically gain permission to perform that action. Record observations and check the terminal condition after every step.

5. Step-by-step algorithm

  1. System policy: Process the system policy stage, and pass its defined output to the next node.
  2. Developer task: Process the developer task stage, and pass its defined output to the next node.
  3. User request: Process the user request stage, and pass its defined output to the next node.
  4. Retrieved document: Process the retrieved document stage, and pass its defined output to the next node.
  5. Context assembler: Process the context assembler stage, and pass its defined output to the next node.
  6. Model: Emit a result only after verifying the stated conditions.

6. Runnable Python lesson

This module links to 02_tool_registry.py. Some modules reuse an earlier example intentionally: revisit it and identify which concept is newly relevant. The downloadable file is in the examples/ folder.

Run locally: python examples/02_tool_registry.py from the extracted project root. Examples using provider libraries also need the dependencies and credentials explained in Setup.
"""Validated tool registry using only Python standard library."""
from dataclasses import dataclass
from collections.abc import Callable

@dataclass(frozen=True)
class ToolSpec:
    name: str
    fn: Callable[[int, int], int]

def multiply(a: int, b: int) -> int:
    return a * b

REGISTRY = {"multiply": ToolSpec("multiply", multiply)}

def execute(name: str, arguments: dict) -> int:
    if name not in REGISTRY:
        raise PermissionError("Unknown or prohibited tool")
    if set(arguments) != {"a", "b"} or any(type(v) is not int for v in arguments.values()):
        raise ValueError("Arguments must be integer a and b")
    return REGISTRY[name].fn(**arguments)

if __name__ == "__main__":
    print(execute("multiply", {"a": 6, "b": 7}))

8. Real-world design exercise

You are building a prompts and context engineering capability for an enterprise assistant. It must complete a user task while preserving authorization, explicit failure states, and observable results.

Build task: Create a typed prompt constructor. Start with one valid scenario, one invalid input and one failure case. Add an explicit max-step or timeout condition and document whether the workflow has side effects.

9. Common mistakes and troubleshooting

  • Executing instructions found in retrieved PDFs. Mitigation: make this condition explicit in a test or a runtime policy.
  • Allowing untrusted tool output to overwrite policy. Mitigation: make this condition explicit in a test or a runtime policy.

10. Practice and knowledge check

In prompt trust-boundary diagram, what happens between “Developer task” and “Model”, and what must be checked?

Follow the labeled arrows in the diagram: Developer task hands a defined result through the intermediate stages toward Model. For this topic, explicitly guard against executing instructions found in retrieved pdfs.

How do you stop an agent from looping forever?

Use a maximum step count, time limit, cost budget and explicit terminal condition.

How do you prove that the result is correct?

Use independent deterministic validation, trusted source evidence, tests and human approval as appropriate.
