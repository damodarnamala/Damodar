Local and open-weight models

Learning outcome: Use local inference through provider-compatible APIs

1. What is it?

Local models can lower per-call service costs and keep data near the device, but they still need sufficient RAM, stable endpoints and robust tool-call parsing.

2. Why does it matter?

Benchmark structured output correctness on your actual hardware.

Concrete scenario: Run a quantized model on local hardware. The figure below names the actual components and shows how information moves among them.

4. Topic-specific architecture and execution flow

Every branch is controlled by application code. A model can recommend an action, but it does not automatically gain permission to perform that action. Record observations and check the terminal condition after every step.

5. Step-by-step algorithm

  1. Agent client: Process the agent client stage, and pass its defined output to the next node.
  2. Local API endpoint: Process the local api endpoint stage, and pass its defined output to the next node.
  3. Tokenizer: Process the tokenizer stage, and pass its defined output to the next node.
  4. Model runtime: Process the model runtime stage, and pass its defined output to the next node.
  5. KV cache / GPU: Process the kv cache / gpu stage, and pass its defined output to the next node.
  6. Generated response: Emit a result only after verifying the stated conditions.

6. Runnable Python lesson

This module links to 07_langchain_agent.py. Some modules reuse an earlier example intentionally: revisit it and identify which concept is newly relevant. The downloadable file is in the examples/ folder.

Run locally: python examples/07_langchain_agent.py from the extracted project root. Examples using provider libraries also need the dependencies and credentials explained in Setup.
"""Requires: pip install langchain langchain-openai and OPENAI_API_KEY."""
from langchain.agents import create_agent
from langchain.tools import tool

@tool
def get_policy(topic: str) -> str:
    """Return the demonstration policy for a topic."""
    return {"refund": "Demo refund window: 14 days."}.get(topic.lower(), "No matching policy")

agent = create_agent(model="openai:gpt-4.1-mini", tools=[get_policy],
                     system_prompt="Answer policy questions; call get_policy when relevant.")

if __name__ == "__main__":
    result = agent.invoke({"messages": [{"role": "user", "content": "Explain refund policy"}]})
    print(result["messages"][-1].content)

8. Real-world design exercise

You are building a local and open-weight models capability for an enterprise assistant. It must complete a user task while preserving authorization, explicit failure states, and observable results.

Build task: Call a configured local model endpoint. Start with one valid scenario, one invalid input and one failure case. Add an explicit max-step or timeout condition and document whether the workflow has side effects.

9. Common mistakes and troubleshooting

  • Assuming every local model supports tool calling. Mitigation: make this condition explicit in a test or a runtime policy.
  • Ignoring RAM and context growth. Mitigation: make this condition explicit in a test or a runtime policy.

10. Practice and knowledge check

In local model inference stack, what happens between “Local API endpoint” and “Generated response”, and what must be checked?

Follow the labeled arrows in the diagram: Local API endpoint hands a defined result through the intermediate stages toward Generated response. For this topic, explicitly guard against assuming every local model supports tool calling.

How do you stop an agent from looping forever?

Use a maximum step count, time limit, cost budget and explicit terminal condition.

How do you prove that the result is correct?

Use independent deterministic validation, trusted source evidence, tests and human approval as appropriate.

Interview angle
