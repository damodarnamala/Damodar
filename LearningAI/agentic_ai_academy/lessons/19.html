Agent-to-agent communication

Learning outcome: Exchange validated messages across agent boundaries

1. What is it?

Agent-to-agent exchange needs messages with task IDs, versions, origin, expected output and an expiration. External agents should be treated like external APIs, not trusted coworkers.

2. Why does it matter?

Enforce authentication and schema validation on each boundary.

Concrete scenario: Exchange a long-running job across services. The figure below names the actual components and shows how information moves among them.

4. Topic-specific architecture and execution flow

Every branch is controlled by application code. A model can recommend an action, but it does not automatically gain permission to perform that action. Record observations and check the terminal condition after every step.

5. Step-by-step algorithm

  1. Agent A: Process the agent a stage, and pass its defined output to the next node.
  2. Discover agent card: Process the discover agent card stage, and pass its defined output to the next node.
  3. Authenticated request: Process the authenticated request stage, and pass its defined output to the next node.
  4. Agent B task queue: Process the agent b task queue stage, and pass its defined output to the next node.
  5. Progress / result: Process the progress / result stage, and pass its defined output to the next node.
  6. Agent A receives: Emit a result only after verifying the stated conditions.

6. Runnable Python lesson

This module links to 02_tool_registry.py. Some modules reuse an earlier example intentionally: revisit it and identify which concept is newly relevant. The downloadable file is in the examples/ folder.

Run locally: python examples/02_tool_registry.py from the extracted project root. Examples using provider libraries also need the dependencies and credentials explained in Setup.
"""Validated tool registry using only Python standard library."""
from dataclasses import dataclass
from collections.abc import Callable

@dataclass(frozen=True)
class ToolSpec:
    name: str
    fn: Callable[[int, int], int]

def multiply(a: int, b: int) -> int:
    return a * b

REGISTRY = {"multiply": ToolSpec("multiply", multiply)}

def execute(name: str, arguments: dict) -> int:
    if name not in REGISTRY:
        raise PermissionError("Unknown or prohibited tool")
    if set(arguments) != {"a", "b"} or any(type(v) is not int for v in arguments.values()):
        raise ValueError("Arguments must be integer a and b")
    return REGISTRY[name].fn(**arguments)

if __name__ == "__main__":
    print(execute("multiply", {"a": 6, "b": 7}))

8. Real-world design exercise

You are building a agent-to-agent communication capability for an enterprise assistant. It must complete a user task while preserving authorization, explicit failure states, and observable results.

Build task: Validate inter-agent messages. Start with one valid scenario, one invalid input and one failure case. Add an explicit max-step or timeout condition and document whether the workflow has side effects.

9. Common mistakes and troubleshooting

  • Treating remote peers as fully trusted. Mitigation: make this condition explicit in a test or a runtime policy.
  • Retrying tasks without stable identifiers. Mitigation: make this condition explicit in a test or a runtime policy.

10. Practice and knowledge check

In a2a remote task lifecycle, what happens between “Discover agent card” and “Agent A receives”, and what must be checked?

Follow the labeled arrows in the diagram: Discover agent card hands a defined result through the intermediate stages toward Agent A receives. For this topic, explicitly guard against treating remote peers as fully trusted.

How do you stop an agent from looping forever?

Use a maximum step count, time limit, cost budget and explicit terminal condition.

How do you prove that the result is correct?

Use independent deterministic validation, trusted source evidence, tests and human approval as appropriate.
