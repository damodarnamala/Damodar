Reflection & verification

Learning outcome: Evaluate an output using deterministic checks

1. What is it?

Verification should first use objective criteria such as tests, JSON schemas, checksums and approved sources. A separate model-based critic can supplement but not replace objective validation.

2. Why does it matter?

Use a finite repair budget and escalate when constraints cannot be satisfied.

Concrete scenario: Verify a code patch with tests. The figure below names the actual components and shows how information moves among them.

3. Key concepts and vocabulary

ConceptExplanation
Validatorobjective success check
Criticfeedback that may be fallible
Repair budgetmax number of revisions
Verification evidencetest report or checked source

4. Topic-specific architecture and execution flow

Every branch is controlled by application code. A model can recommend an action, but it does not automatically gain permission to perform that action. Record observations and check the terminal condition after every step.

5. Step-by-step algorithm

  1. Generate candidate: Process the generate candidate stage, and pass its defined output to the next node.
  2. Schema validator: Process the schema validator stage, and pass its defined output to the next node.
  3. Run unit tests: Process the run unit tests stage, and pass its defined output to the next node.
  4. Fail report: Process the fail report stage, and pass its defined output to the next node.
  5. Repair boundedly: Process the repair boundedly stage, and pass its defined output to the next node.
  6. Verified output: Emit a result only after verifying the stated conditions.

"""Run: python -m unittest discover -s examples -p 'test_*.py'"""
import unittest
from importlib.machinery import SourceFileLoader
from pathlib import Path

MODULES = Path(__file__).parent
planner = SourceFileLoader("planner", str(MODULES / "04_planner.py")).load_module()

class TestPlanner(unittest.TestCase):
    def test_order(self):
        order = planner.schedule({"build": ["plan"], "plan": []})
        self.assertEqual(order, ["plan", "build"])

    def test_cycle(self):
        with self.assertRaises(ValueError):
            planner.schedule({"a": ["b"], "b": ["a"]})

if __name__ == "__main__":
    unittest.main()

Code-reading checklist for Generate–validate–repair cycle: locate the input contract, identify where the “Schema validator” responsibility appears, and check how output reaches “Verified output”. The reusable example may demonstrate only one part of the architecture; do not mistake it for a complete implementation.

8. Real-world design exercise

You are building a reflection & verification capability for an enterprise assistant. It must complete a user task while preserving authorization, explicit failure states, and observable results.

Build task: Build a validation-repair loop. Start with one valid scenario, one invalid input and one failure case. Add an explicit max-step or timeout condition and document whether the workflow has side effects.

9. Common mistakes and troubleshooting

  • Using model self-confidence instead of tests. Mitigation: make this condition explicit in a test or a runtime policy.
  • Infinite critic–generator ping-pong. Mitigation: make this condition explicit in a test or a runtime policy.

10. Practice and knowledge check

In generate–validate–repair cycle, what happens between “Schema validator” and “Verified output”, and what must be checked?

Follow the labeled arrows in the diagram: Schema validator hands a defined result through the intermediate stages toward Verified output. For this topic, explicitly guard against using model self-confidence instead of tests.

How do you stop an agent from looping forever?

Use a maximum step count, time limit, cost budget and explicit terminal condition.

How do you prove that the result is correct?

Use independent deterministic validation, trusted source evidence, tests and human approval as appropriate.

Hands-on assignment

Modify 12_tests.py to log each step as a dictionary containing step, action, status and elapsed_ms. Then write tests for one success case and one rejection case.

Interview angle

Design interview: You need to verify a code patch with tests. Defend the boundaries between generate candidate and verified output, describe how to handle “using model self-confidence instead of tests”, and identify a measurable acceptance test.
