Browser and coding agents

Learning outcome: Use sandboxed execution and reviewable patches

1. What is it?

Coding and browser agents interact with mutable environments. Their actions should be sandboxed, observable and reviewable. A patch is a proposal until tests and review have passed.

2. Why does it matter?

Avoid unrestricted terminal execution, credential exposure and hidden side effects.

Concrete scenario: Modify a repository only after validating changes. The figure below names the actual components and shows how information moves among them.

4. Topic-specific architecture and execution flow

Every branch is controlled by application code. A model can recommend an action, but it does not automatically gain permission to perform that action. Record observations and check the terminal condition after every step.

5. Step-by-step algorithm

  1. Read-only repo scan: Process the read-only repo scan stage, and pass its defined output to the next node.
  2. Plan patch: Process the plan patch stage, and pass its defined output to the next node.
  3. Sandbox edit: Process the sandbox edit stage, and pass its defined output to the next node.
  4. Run tests: Process the run tests stage, and pass its defined output to the next node.
  5. Review diff: Process the review diff stage, and pass its defined output to the next node.
  6. PR proposal: Emit a result only after verifying the stated conditions.

"""Illustrates approval tied to an exact proposed action digest."""
import hashlib
import json

def digest(action: dict) -> str:
    data = json.dumps(action, sort_keys=True, separators=(",", ":")).encode()
    return hashlib.sha256(data).hexdigest()

class ApprovalGate:
    def __init__(self):
        self.approved = set()

    def authorize(self, action: dict, reviewer: str):
        if not reviewer:
            raise ValueError("Reviewer identity required")
        self.approved.add(digest(action))

    def permitted(self, action: dict) -> bool:
        return digest(action) in self.approved

if __name__ == "__main__":
    gate = ApprovalGate()
    action = {"type": "deploy", "version": "1.0.0"}
    gate.authorize(action, "authorized-reviewer-demo")
    assert gate.permitted(action)
    assert not gate.permitted({**action, "version": "2.0.0"})
    print("Approval is action-specific")

8. Real-world design exercise

You are building a browser and coding agents capability for an enterprise assistant. It must complete a user task while preserving authorization, explicit failure states, and observable results.

Build task: Build a safe code change plan. Start with one valid scenario, one invalid input and one failure case. Add an explicit max-step or timeout condition and document whether the workflow has side effects.

9. Common mistakes and troubleshooting

  • Running arbitrary repository scripts unsandboxed. Mitigation: make this condition explicit in a test or a runtime policy.
  • Merging generated code without human review. Mitigation: make this condition explicit in a test or a runtime policy.

10. Practice and knowledge check

In coding agent safe change sequence, what happens between “Plan patch” and “PR proposal”, and what must be checked?

Follow the labeled arrows in the diagram: Plan patch hands a defined result through the intermediate stages toward PR proposal. For this topic, explicitly guard against running arbitrary repository scripts unsandboxed.

How do you stop an agent from looping forever?

Use a maximum step count, time limit, cost budget and explicit terminal condition.

How do you prove that the result is correct?

Use independent deterministic validation, trusted source evidence, tests and human approval as appropriate.
